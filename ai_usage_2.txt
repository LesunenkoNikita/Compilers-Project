3. WHAT I TOOK AS IT WAS, WHAT I CHANGED AND WHY
-----------------------------------------------

Language design (my part): the emojis and the shape of the new constructs are mine — ⚙️ for functions, 🔙 as
return, 🏰 for structures with fields declared like variables, 🛠️ for member functions, 📖 and 🖨️ with the value
in parentheses, field chains with ".". The Stage 1 syntax is unchanged.

Decisions the AI made that I accepted as they were:
- arithmetic ➕ ➖ ✖️ (the PDF needs arithmetic in code generation, and Stage 1 had none; ASCII "-" stays a
  lexical error so the Stage 1 test still passes);
- an object is created with Name(values...), one value per field that has no "=> default";
- 📖(target) is a statement that reads into a mutable integer variable or field;
- 🚪 prints "Program exit with result V" and exits with V as the exit status;
- an i64 stored into an i32 is allowed but checked at run time (so the Stage 1 program full_program, which assigns
  an i64 constant to an i32 variable, stays valid as the PDF requires);
- arithmetic overflow is checked at run time; integer literals are range-checked at compile time (the fix for the
  Stage 1 review comment about out-of-range i32 literals).

grammar.ebnf — taken as generated, then changed after prompt 2: the first version allowed 🔙 only as the last
line of a function body. That was not what I meant: 🔙 is return, so it is now an ordinary statement inside
function bodies at any depth.

README_TASK1.md and README.md — taken as generated (examples per feature, 21 rules, each with a test that follows
it and a test that breaks it, build/run/test instructions). Changed after prompt 2: the 🔙 explanation, the
factorial example (now with an early return) and rule 14 (every path must leave the function with 🔙 or 🚪).

task2compiler.py (Task 2, lexer + parser + --ast) — taken as generated: new tokens in the keyword automaton,
string literals, one parser method per grammar rule, new AST nodes. Changed after prompt 2: 🔙 is parsed as a
statement anywhere inside a function body; outside a function it is a syntax error.

compiler.py (Task 3, semantic pass + LLVM IR through the llvmlite builder) — taken as generated. Changed after
prompt 2: the semantic pass checks every 🔙 against the result type and checks that every path through a function
ends in 🔙 or 🚪; code generation emits a "ret" for each 🔙 and puts the code after it into a dead block. Changed
after my venv mistake: the lazy llvmlite import described above.

run_tests.py — taken as generated: compares --ast with NAME.ast (creates it when missing), compiles to
build/NAME.ll, runs it with lli (or llc + clang with --native) using NAME.in as standard input, compares with
NAME.expected; for invalid programs it compares the error line and checks that no .ll file is written. Changed
later: the Python / LLVM tool discovery described above.

Tests — the Stage 1 tests were kept: their old AST .expected files became .ast files and got new .expected files
with the program output. The Stage 1 test literal_beyond_i32_still_parses moved to
tests/errors/sem_literal_beyond_i32_still_parses, because the overflow check now rejects it (it still parses, its
.ast is the Stage 1 AST). New tests were generated; after prompt 2 syn_statement_after_return was removed (it is
legal now), syn_function_without_return became sem_function_without_return, and func_early_return,
sem_return_missing_on_one_path and sem_return_wrong_type_in_branch were added. Result: 49 valid (all end to end,
two with .in input) and 96 invalid programs, all passing with lli and with llc + clang.

test.txt / test.expected — taken as generated: a program using every new construct and its AST from
task2compiler.py --ast.
