3. WHAT I TOOK AS IT WAS, WHAT I CHANGED AND WHY
-----------------------------------------------

Task 1, encapsulation (compiler.py, grammar.ebnf, README.md, tests) — my part: choosing this feature from the PDF
menu, the 🔓 and 🔒 emojis, public as the default, and private fields being settable in the constructor. Taken as
generated: the lexer token, the parser rule, the semantic checks, the error messages that name the member, the 20
encapsulation_ tests, the README rules, the two example programs and the IR excerpt. One decision the AI made that I
accepted: 🖨️ of an object hides private fields unless it runs inside a member function of that structure, because
otherwise a private value could be read from outside by printing the object. I did not change this code.

Task 2, optimizer (compiler.py, README.md, tests/optimizer) — taken as generated: the --optimize flag and the three
transformations. Decisions the AI made that I accepted:
- an unused variable stays if its expression can stop the program with an overflow or range error, because removing
  it could change what the program prints; an expression that is exactly a call becomes a call statement;
- unused functions are found by what the top-level code reaches, and this also removes unused member functions;
- only plain functions with one 🔙 as the last statement are inlined; recursive functions, early returns and member
  functions are left alone, and so is a call that cannot move without changing the order of effects;
- inlined locals are named like add$1$a, because $ cannot appear in a source name.

run_tests.py — the first version generated for Task 2 ran every test twice, without and with --optimize. I changed
that with prompt 3: without the flag it runs tests as before, and only "python3 run_tests.py --optimize" uses the
optimizer, because I wanted to choose the mode myself. For Task 3 the AI added the programs/ sessions.

Task 3, the real program (programs/safe.txt, its sessions, README.md) — this part changed the most, and the changes
came from me:
- From the options the AI listed, I chose a safe with a lock (prompt 6). The first version let one person choose the
  code and then store coins through menus.
- That made no sense as a game: one person always knows the code, and the coins came from nowhere. So I redesigned it
  (prompt 9): two players, a 4-digit code, 10 tries, hints about digits and positions, no coins except the 9999 prize.
- The first hint rule gave too much away for repeated digits, so I corrected it (prompt 10): against 1234, the guess
  1111 must print only that 1 is at position 1. Now each digit of the code gives at most one hint.
- The next version split a typed number into digits by counting up from 0000, because the language has no division.
  I replaced that with separate entries (prompt 11): Player 1 gets four prompts, one per digit, and Player 2 types
  the digits separated by spaces. That removed the counting search from the program.
- The AI decided on these details and I accepted them: 40 empty lines to hide the code, re-asking after an invalid
  entry without using a try, and the session names safe and safe_locked.

Compiler change for the game — 🖨️ could print only one value per line, so a hint such as "Digit 3 is in the code, but
not at position 3" was impossible. To support my hint messages, the AI extended 🖨️ to several comma-separated values
on one line, with tests, grammar and README updates. Existing programs print the same.

Tests — taken as generated. The expected output of the tests was written before running them, and the expected output
of the game sessions came from a separate Python version of the hint rules, not from the compiler. Some first
attempts had wrong line or column numbers in the expected files, and those files were corrected.


4. WHAT I UNDERSTOOD
--------------------

Encapsulation is only a compile-time check. Lexer, parser and semantic pass do most of the job, lexer and parser state 
if a member is private, semantic pass compares the structure of the member with the structure whose member function 
is checked. For example, the viewer() has the method's structure, and if the private field's structure and method's 
structure are not the same, it reports an error with the member's name. In the generated IR a private field is a 
getelementptr, so privacy costs nothing at run time.

The optimizer works on the checked tree, after the semantic pass and before code generation.
